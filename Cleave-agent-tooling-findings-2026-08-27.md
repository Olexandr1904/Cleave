# Cleave: чому результат агентів гірший за роботу з Claude у терміналі

**Дата дослідження:** 2026-08-27
**Репозиторій:** https://github.com/Olexandr1904/Cleave
**Гілка / коміт на момент аналізу:** `master` @ `950d644` («fix: harden run.sh restart and Android SDK lookup across hosts», 2026-06-03)
**Обсяг кодової бази:** ~39 700 рядків Python, 205 `.py`-файлів
**Метод:** статичний аналіз джерел. Пайплайн не запускався, живих прогонів не спостерігалось.

> **Як користуватись цим документом.** Це інструкція для агента, який працюватиме
> в репозиторії Cleave. Розділи 1-2 — контекст і що вже перевірено (не перевіряй
> заново). Розділ 3 — знахідки з доказами. Розділ 4 — що робити. Розділ 5 —

> як писати код.

## 1. Передісторія

Питання, з якого все почалось: чому автономні агенти Cleave дають гірший
результат, ніж коли та сама модель просто працює з людиною в терміналі Claude Code.

Гіпотеза, з якою заходили: підозра на архітектурну ваду — що Cleave використовує
Claude як «генератор тексту», сам реалізує ReAct-цикл і тому втрачає всі переваги
справжнього агентського циклу. Така вада реально існує в іншому проєкті автора
(AI Dashboard POC), і питання було, чи повторена
вона тут.

**Гіпотеза не підтвердилась.** Див. розділ 2.

## 2. Що виявилось зробленим правильно (НЕ чіпати)

### 2.1. Claude Code запускається як повноцінний агент, а не як генератор тексту

`integrations/llm/claude_code_adapter.py:190` — метод `execute_in_workspace()`
запускає `claude -p` у робочій теці тікета і віддає керування tool-циклом самому
Claude Code:

```
cmd = [claude, "-p",
       "--model", <model>,
       "--output-format", "stream-json", "--verbose",
       "--max-turns", <turns>,
       "--allowedTools", <csv>,
       "--add-dir", <meta_dir>]
cwd = <workspace source dir>
```

Рішення зафіксоване в коді явно:

- `claude_code_adapter.py:184` — `send_tool_results()` кидає `NotImplementedError`
  з текстом *«ClaudeCodeAdapter handles tool execution internally. Use
  execute_in_workspace() instead of the multi-turn tool loop.»*
- `claude_code_adapter.py:6-8` (докстрінг модуля) — *«Claude Code handles its own
  tool execution internally (Read, Write, Bash, etc.), so the ToolSandbox is not
  used with this adapter.»*
- `orchestrator/agent_runtime.py:465` — *«Claude Code handles its own tool loop
  internally — our max_tool_rounds budget doesn't apply here.»*

Це правильна архітектура. Переписувати її не треба.

### 2.2. Операційна обв'язка навколо CLI — зріла

Написана явно по слідах реальних інцидентів (у коментарях згадані тікети
ACME-3887, ACME-13824, ACME-6941):

| Механізм | Місце | Призначення |
|---|---|---|
| Пособітійний парсинг `stream-json` | `claude_code_adapter.py:315` (`_run_cli`), `:881` (`_handle_stream_event`) | видимість прогресу в реальному часі, а не очікування кінця процесу |
| Heartbeat кожні 30 с | `HEARTBEAT_INTERVAL_SECONDS = 30` | стало видно «висить N хвилин» |
| Watchdog після `result` | `POST_RESULT_IDLE_GRACE_SECONDS = 600` | CLI віддав результат, але процес не вийшов — забрати результат і вбити |
| Watchdog до `result` | `IDLE_STALL_SECONDS = 1800` | зависання посеред tool-виклику |
| Вбивство групи процесів | `os.killpg` у `_run_cli` | забирає і CLI, і породжені ним інструменти |
| Розпізнавання квоти | `_classify_cli_error`, `_stall_as_quota`, `QuotaExhaustedError` | rate-limit → DEFERRED з реальним часом ресету, а не FAILED |
| Tee сирого стріму | `raw_stream_path` → `<agent>.stream.jsonl` | форензика поганих прогонів |

Це все працює на користь якості. Не спрощувати.

### 2.3. Бюджети — щедрі, не вони вузьке місце

`config/schemas.py:36` (`AgentBudget`):

```
max_cli_turns     = 100          # прокидається в --max-turns
wall_clock_seconds = 14_400      # 4 години
max_total_tokens   = 15_000_000
```

Плюс `agent_budget_overrides` — по-агентні перекриття (`config/schemas.py:86`).
`agent_runtime.py:498` реально передає `max_turns=budget.max_cli_turns`.

Тобто по стелі часу й токенів простору вдосталь. Єдина потенційно тісна ручка —
100 ходів, і в коментарі поруч уже зафіксовано, що 50 було замало. Це **конфіг**,
а не код. Пріоритет низький.

## 3. Знахідки: що саме створює розрив із терміналом

Впорядковано за очікуваним впливом.

### 3.1. КРИТИЧНО — агентам доступно шість інструментів із двох десятків

`integrations/llm/claude_code_adapter.py:130`:

```python
TOOL_MAP = {
    "read_file":      "Read",
    "write_file":     "Write,Edit",
    "list_directory": "LS,Glob",
    "search_code":    "Grep",
    "run_command":    "Bash",
    "git_operation":  "Bash",
}
```

`_map_tools()` (`:665`) мапить внутрішні імена в імена інструментів Claude Code, і
результат іде у `--allowedTools`. Це **allowlist** — усе, чого немає в мапі,
недоступне фізично.

Фактичні гранти по агентах (`agents/*.md`, блок `tools:`):

| Агент | Гранти | → інструменти Claude Code |
|---|---|---|
| ba-agent | read_file, list_directory, search_code | Read, LS, Glob, Grep |
| dev-agent | + write_file, run_command, git_operation | + Write, Edit, Bash |
| fix-agent | те саме, що dev | Read, Write, Edit, LS, Glob, Grep, Bash |
| qa-agent | те саме, що dev | те саме |
| scope-guard-agent | read_file, list_directory, search_code, git_operation | Read, LS, Glob, Grep, Bash |
| pr-comment-responder | read_file, list_directory, search_code | Read, LS, Glob, Grep |

Чого немає **в жодного** агента:

- **`Task`** — сабагенти. Не можна розпаралелити дослідження по підсистемах,
  не можна винести широкий пошук в окремий контекст. У терміналі це один із
  головних інструментів на складних задачах.
- **`Skill`** — навички. Недоступні `superpowers:test-driven-development`,
  `systematic-debugging`, `brainstorming`, `writing-plans` — тобто рівно ті
  процеси, які автор прописав у власному `CLAUDE.md` як обов'язкові. Агент, що
  пише код, не має доступу до TDD-скіла.
- **`WebSearch` / `WebFetch`** — не подивиться документацію бібліотеки, changelog,
  issue на GitHub.
- **`TodoWrite`** — немає структурованого ведення багатокрокової задачі; план
  живе тільки в тексті промпту.
- **MCP-інструменти** — Jira/Atlassian/GitHub доступні лише через власний
  Python-шар `integrations/`, всередині агентського циклу їх немає.

Це найбільший і найдешевший для усунення розрив.

### 3.2. ВИСОКИЙ — стадії пайплайну не мають спільної розмови

`--resume` і `--continue` не використовуються ніде в кодовій базі. Перевірено
grep-ом по всіх `.py`: єдина згадка `session_id` — це логування init-івенту
(`claude_code_adapter.py:895`), сам ідентифікатор нікуди не зберігається.

Наслідок: `BA → DEV → SCOPE_CHECK → QA → FIX` — це **п'ять холодних процесів**.
Кожен стартує з нуля, отримує зібраний нами брифінг і не має доступу до
міркувань попередника — лише до артефактів на диску.

Найболючіше місце — цикл `QA (fail) → DEV`: агент, що виправляє, не пам'ятає,
чому початкова реалізація була саме такою, і схильний переписувати замість
точкового виправлення.

У терміналі це одна нитка, де вся історія міркувань фізично присутня.

### 3.3. СЕРЕДНІЙ — контекст нарізається наперед замість читання за потребою

`orchestrator/agent_runtime.py:32-49`:

```python
_PER_FILE_CONTEXT_BYTES = 5000
_TOTAL_CONTEXT_BYTES    = 100_000
_CONTEXT_FILE_PRIORITY  = {"ticket.md": 0, "parent.md": 1, "history.md": 2, "comments.md": 3}
```

Файли з `meta_dir` вклеюються в промпт за пріоритетом, обрізаються по 5 КБ на
файл і сумарно по 100 КБ. Балакучий тред коментарів у Jira приїде обрубаним.

Іронія в тому, що `meta_dir` **і так** відданий агентові через `--add-dir`
(`agent_runtime.py:495`) — тобто він може прочитати ці файли сам, цілком і
вибірково. Попереднє вклеювання дублює роботу і при цьому втрачає дані.

### 3.4. СЕРЕДНІЙ, але це компроміс дизайну — немає людини в стерні

Cleave — демон. Одна спроба на стадію, ескалація в Telegram спрацьовує лише
коли пайплайн **застряг** (BLOCKED/DEFERRED/FAILED), а не коли він упевнено
робить не те.

У терміналі людина коригує курс кожні дві-три репліки. Це, ймовірно, найбільша
одинична складова розриву — і жодне технічне покращення її повністю не закриє.
Це ціна автономності, свідомо сплачена. Пом'якшити можна (див. 4.4), усунути — ні.

### 3.5. НИЗЬКИЙ — стеля в 100 ходів

Див. 2.3. Це конфіг-ручка `AgentBudget.max_cli_turns`, уже по-агентна. Якщо
після 4.1 агенти почнуть викликати сабагентів і скіли, ходи витрачатимуться
швидше — тоді підняти для dev/fix до 200-300 і подивитись на факті.

## 4. Що пропоную зробити

Порядок важливий: 4.1 → перевірка на живому тікеті → 4.2 → і далі.
Не робити все одразу — інакше не буде видно, що саме дало ефект.

### 4.1. P0 — розширити `TOOL_MAP` і гранти агентів

**Мета:** дати агентам ті самі можливості, що має Claude у терміналі.

**Зміни:**

1. `integrations/llm/claude_code_adapter.py:130` — додати нові логічні імена
   (не розширювати наявні, щоб гранти лишались явними й аудитованими):

   ```python
   TOOL_MAP = {
       # наявні
       "read_file":      "Read",
       "write_file":     "Write,Edit",
       "list_directory": "LS,Glob",
       "search_code":    "Grep",
       "run_command":    "Bash",
       "git_operation":  "Bash",
       # нові
       "web_research":   "WebSearch,WebFetch",
       "plan_tasks":     "TodoWrite",
       "delegate":       "Task",
       "use_skill":      "Skill",
   }
   ```

2. `agents/*.md`, блок `tools:` — роздати вибірково, а не всім однаково:

   | Агент | Додати | Обґрунтування |
   |---|---|---|
   | ba-agent | `web_research`, `plan_tasks`, `delegate` | аналіз вимог виграє від паралельного дослідження і від зовнішніх доків |
   | dev-agent | `web_research`, `plan_tasks`, `delegate`, `use_skill` | основний бенефіціар; TDD-скіл саме тут |
   | fix-agent | `web_research`, `plan_tasks`, `use_skill` | `delegate` не даю: задача точкова, сабагенти радше нашкодять |
   | qa-agent | `web_research`, `plan_tasks` | діагностика падінь тестів часто впирається в зовнішні доки |
   | scope-guard-agent | **нічого** | це суддя; вузький інструментарій — його гарантія неупередженості |
   | pr-comment-responder | `web_research`, `use_skill` | — |

3. `.claude/settings.json` — додати нові інструменти в `permissions.allow`:
   `WebSearch`, `WebFetch`, `TodoWrite`, `Task`, `Skill`. Блок `deny` не чіпати.

**Ризики й на що дивитись:**

- Токени зростуть відчутно. `Task` і `Skill` — найдорожчі. Стеля 15M має
  витримати, але після першого прогону звірити фактичне споживання з
  `max_total_tokens` і за потреби підняти `max_cli_turns` (див. 3.5).
- `delegate` не давати scope-guard і fix — це навмисно.

### 4.2. P0 — `--resume` у межах одного тікета

**Мета:** зберегти нитку міркувань між стадіями, насамперед у циклі QA → Fix.

**Зміни:**

1. `claude_code_adapter.py` — `session_id` уже парситься з init-івенту
   (`:895`). Зберегти його в `_ProgressState`, потім прокинути в `LLMResponse`
   (додати поле `session_id: str = ""` у `llm_interface.py:19`).
2. `execute_in_workspace()` — новий параметр `resume_session_id: str | None`;
   якщо переданий, додати `--resume <id>` у `cmd`.
3. `agent_runtime.py` — після успішного виклику записати `session_id` у стан
   воркспейсу; на наступній стадії того ж тікета прочитати й передати.
4. `workflows/default-workflow.yaml` — зробити це **opt-in по стадії**, поле на
   кшталт `resume_from_previous: true`.

**Кому вмикати:**

- **Так:** `FIX` (продовжує DEV), повторний `DEV` після провалу QA.
- **Ні:** `SCOPE_CHECK` — він має судити свіжим поглядом; `BA` — початок роботи.

**Ризики:**

- `--resume` тягне повний попередній контекст → токени ростуть. Це і є ціна.
- Сесія CLI прив'язана до свого сховища; якщо воркспейс перестворено або сесія
  протухла, `--resume` впаде. **Обов'язково** зробити fallback на холодний старт
  із логуванням, а не падіння тікета.
- Перевірити, що `--resume` сумісний з `-p` і `--output-format stream-json` у
  версії CLI, яка стоїть на хості (див. 6.2).

### 4.3. P1 — віддати `meta_dir` агентові замість вклеювання

**Мета:** прибрати втрату даних на обрізанні й дублювання роботи.

**Зміни в `agent_runtime.py`:** замість збирання вмісту файлів у промпт —
передати **перелік шляхів** із одним рядком опису кожного, і в промпті вказати:
«деталі читай сам з `meta/`». Тека вже доступна через `--add-dir`.

Компроміс: `ticket.md` варто лишити вклеєним (агент має бачити суть задачі
одразу, без зайвого ходу), а `comments.md` / `history.md` / `parent.md` —
віддати як шляхи. Тобто `_CONTEXT_FILE_PRIORITY` перетворюється на «що інлайнимо»
проти «що згадуємо».

### 4.4. P2 — пом'якшити відсутність людини

Не усуває 3.4, але звужує розрив. Ідеї в порядку співвідношення користь/ціна:

1. **Самокритика перед здачею стадії.** Окремий короткий виклик: «ось задача,
   ось діф — що тут не так?». Дешево, ловить очевидні промахи. Це вже частково
   робить scope-guard, але він перевіряє *межі* змін, а не *якість*.
2. **Чекпоінт на плані.** Після BA слати в Telegram план і давати 10 хвилин на
   «ні, не так» перед стартом DEV. Одна точка втручання там, де вона найдешевша.
3. **Ескалація за невпевненістю, а не лише за застряганням.** Якщо агент у
   висновку сам відзначає неоднозначність — не мовчати, а спитати.

## 5. Чого не чіпати

- Архітектуру `execute_in_workspace` (розділ 2.1) — вона правильна.
- Watchdog-и, heartbeat, `killpg`, класифікацію квоти (2.2) — написані по
  реальних інцидентах, кожна константа має обґрунтування в коментарі поруч.
- Блок `deny` у `.claude/settings.json`.
- Гранти scope-guard — його вузькість навмисна.
- `ToolSandbox` (`orchestrator/tool_sandbox.py`) — на CLI-шляху не
  використовується взагалі; це шлях API-адаптера. Не плутати.

## 6. Закрити емпірично ДО написання коду

1. **Чи успадковують сабагенти (`Task`) обмеження `--allowedTools` батька?**
   Якщо ні — `delegate` пробиває пісочницю, і гранти треба переглянути.
2. **Чи працює `--resume` разом з `-p --output-format stream-json`** у версії
   CLI на цільовому хості? Перевірити руками до реалізації 4.2.
3. **Під яким `CLAUDE_CONFIG_DIR` працює демон?** Адаптер його не виставляє
   (на відміну від dashboard-проєкту), тобто успадковує оточення процесу. Від
   цього залежить, які саме скіли й плагіни побачить `Skill` — і чи побачить
   узагалі.
4. **Чи доступні MCP-сервери** в тому оточенні, і чи варто їх вмикати
   (`mcp__*` в `--allowedTools`) — це окреме рішення, у P0 не входить.

## 7. Порядок робіт і як міряти

1. Закрити питання розділу 6.
2. Реалізувати 4.1. Прогнати **один** реальний тікет середньої складності.
3. Порівняти з попереднім прогоном схожого тікета: кількість ходів, токени,
   чи знадобилось людське втручання, якість дифу.
4. Тільки після цього — 4.2. Знову один тікет, знову порівняння.
5. Далі 4.3, 4.4 за результатами.

Міряти по одному тікету за раз. Якщо змінити все одразу, причину покращення
(або погіршення) встановити не вдасться.

**Робочий процес:** у репозиторії є `tests/unit`, `tests/integration`, `tests/e2e`
і `CONTRIBUTING.md` — зміни до `TOOL_MAP` і `_map_tools` покриваються юніт-тестами
тривіально, почни з них. Діють правила з `CLAUDE.md` автора щодо пріоритету
скілів (TDD через `superpowers:test-driven-development`, налагодження через
`superpowers:systematic-debugging`).
